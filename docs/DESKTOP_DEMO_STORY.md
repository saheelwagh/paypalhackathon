## The story

A freelancer has an agreed $1,000 website project and a $300 deposit. The client asks for a headline correction and a custom hero animation. The correction is included; the animation is a proposed $250 addition. lancepal connects the request to its evidence, compares it with the agreement, and helps the freelancer obtain a clear decision before issuing a separate invoice.

The three-minute recording focuses on that one $250 scope change. The original $1,000 agreement and $300 deposit can be loaded as visibly seeded Demo history. They are starting context, not actions that the recording pretends to perform. The full $300/$250/$700 lifecycle remains available for verification outside this short story.

The outcome is concrete: the included correction remains $0, the accepted extra stays separate from the deposit, and pending money never appears as collected money. Client acceptance is an explicit version-specific decision in the client review surface. Neither a transcript, an assistant answer, nor the freelancer's voice substitutes for that acceptance.

## Command dock and voice controls

The shared command dock stays within reach on Console and Funding and accepts typed commands. Console exposes deterministic Demo commands or live Nebius requests. Funding defaults to **Nebius · natural language** over minimized sandbox context; **local rules** remains an explicitly selected fallback. The execution source stays visible. Draft requests produce a server-resolved preview followed by a separate Prepare action; explicit send review remains later.

A voice command is deliberate and reviewable:

1. Start recording with a visible microphone control that explains audio is sent to AssemblyAI after stopping.
2. Choose **Stop & transcribe** to end capture and submit the recording; the 30-second cap also ends capture. A deliberately selected audio command file follows the same transcription path.
3. Show the returned text for review/correction.
4. Explicitly run the reviewed text in the selected command mode. Transcription never submits the business command automatically.

This iteration targets **recorded-command transcription**. It must not be called streaming STT, continuous listening, or a live voice conversation. Microphone capture by itself is not provider transcription. A typed fallback remains usable when recording, transcription, or model execution fails.

An example command is: “Review Acme's animation request against the agreed scope. Show the evidence, the extra price, and what needs approval.” The implementation must ground its result in the selected project's records. The assistant may investigate and prepare a reviewable next action; explicit owner/client decisions still govern commercial changes.

For a separate Funding cutaway in Nebius mode, ask **“Could you take me to the website project?”** and **“How much has the client paid me so far?”** to open the original sandbox evidence. On a separately identified project with an eligible obligation, record or upload **“Could you get the next invoice ready for this project?”**, review the returned transcript, and Run. Show the exact source/version/amount preview before the separate **Prepare sandbox draft** action. Canceling that preview creates no invoice. Open the prepared local draft to show the unchanged approval/send review; preparation never implies send or collection. The completed reference project has no new next invoice, so inspect its original receipts instead of inventing another obligation. Local rules remain an explicit fixed-phrase fallback, including “inspect deposit invoice” and “prepare change Custom hero animation invoice.”

Funding accepts one supported command at a time, resolves ambiguous names explicitly, and binds preparation to the current selected project, revision, and funding snapshot. Changes during planning/reservation fail closed; repeating a named-purpose preparation opens the original invoice. Agreement, change approval, delivery acceptance, sending, and payment remain separate actions. Pending collection continues to block later stages. The original short Console recording plan below remains a synthetic story; do not blend its seeded amounts with sandbox payment evidence.

Natural-language draft previews expire after two minutes and after server restart; request a fresh preview when needed. Applying uses the frozen source and never asks Nebius to interpret “next” again. This is one reviewed action per request, not continuous dialogue or streaming speech. Real microphone capture remains outside the verified recording path.

## Truth labels

Labels describe each operation or record, not just the whole page. A live provider can inspect synthetic project data without making that project's payments real.

| Label | Meaning in this story |
| --- | --- |
| Seeded history | A synthetic starting agreement, approval, payment, or transcript loaded for the scene. It was not performed by a real client/provider. |
| Simulated command | A deterministic local task plan over current Demo records. No model inference is claimed. |
| Live Nebius | An actual model request completed through the configured Nebius adapter. Its input may still be synthetic, and its response is not financial authority. |
| Funding · Nebius | Interprets natural requests into a single validated view or draft proposal using only minimized sandbox context. The preview requires a separate Prepare action; approval/send/payment authority never belongs to the model. |
| Funding · local rules | A deterministic single-command interpreter over the separate sandbox ledger, not model inference. It may open evidence or prepare a local source-bound draft; it cannot approve, send, or pay. |
| Live recorded transcription | AssemblyAI returned text for the explicitly submitted recording. This does not establish streaming STT or client agreement. |
| Demo invoice/payment | A synthetic invoice or payer outcome. Pending is unresolved, and confirmed means confirmed within the Demo simulation only. |
| Client role preview | A deliberate simulated client decision. It is not authenticated client access. |

Show failures as failures. A failed live provider call must not silently produce a simulated success. Retrying is explicit and preserves the user's reviewed command and existing business records.

## Implementation boundaries

- The short Console story uses synthetic payments. The separate Funding journey has actual PayPal sandbox invoices and verified webhook collection; it uses test funds and fresh local-owner test decisions. Refunds, production money, authenticated client signatures, and model financial execution remain unavailable.
- Nebius command and AssemblyAI recording routes are local-only development endpoints, with bounded inputs/requests and server-side credentials. They do not establish production authentication or a public deployment.
- Talk clearly states that stopping submits audio to AssemblyAI; audio-file selection also submits a recording. Recordings are limited to 30 seconds/8 MB, with best-effort provider-transcript deletion and honest cleanup status. Running the reviewed text is a separate explicit action. Keep credentials and private provider context out of client responses and activity displays.
- Keep generated tool arguments subject to the existing version, exact-money, coverage, and approval rules. A model result cannot record a client acceptance or convert pending payment into confirmed collection.
- PostgreSQL remains deferred until the end. Browser-local synthetic storage remains the financial Demo's persistence boundary; preserve existing environment configuration.
- No publishing, external messaging, deployment, or submission is part of this work.
